## 1. Project Identity

Solarch is a self-contained TypeScript Backend-as-a-Service (BaaS) and application framework inspired by PocketBase. It combines an embedded SQLite database engine (`better-sqlite3`), dynamic schema and record management, rule-based authorization, JWT authentication (admin and record users), multi-factor authentication (MFA/OTP), automated ZIP backups, an event-driven hook system (`Hook` / `TaggedHook`), real-time streaming subscriptions (Server-Sent Events and WebSockets), sandboxed JavaScript execution (Node `vm` and optional Deno subprocess isolation), an integrated LLM service layer (supporting OpenAI, Anthropic, Ollama, and OpenRouter), and an embedded React-based Admin UI served directly under `/_/`.

- **Primary Language:** TypeScript (Node.js ES2022 / CommonJS build output). Frontend in TypeScript React.
- **Core Frameworks:** Express v4 (HTTP routing/middleware), React 18 (Admin UI), Vite 6 (Frontend build tooling), Commander v12 (CLI engine), `better-sqlite3` (Database driver), `ws` (WebSocket server), Vitest (Test runner).
- **Runtime Requirement:** Node.js `>= 20.0.0`. Optional runtime dependency: Deno (for isolated JSVM sandbox execution).
- **Entry Points:**
  - **CLI Entry Point:** [src/cli.ts](file:///Users/jay/Downloads/solarch/src/cli.ts) (binary executable `solarch`, invokes `serve`, `superuser`, `migrate`, `init`).
  - **Library Entry Point:** [src/index.ts](file:///Users/jay/Downloads/solarch/src/index.ts) (exports core models, DB driver, events, utilities, and AI services).
  - **Server Bootstrap:** [src/solarch.ts](file:///Users/jay/Downloads/solarch/src/solarch.ts) (extends `BaseApp`, initializes databases, executes system migrations, loads JS hooks, and launches Express HTTP/WS server).
  - **Admin UI Entry Point:** [admin/src/main.tsx](file:///Users/jay/Downloads/solarch/admin/src/main.tsx) (mounts React SPA built into `pb_public/admin`).

### Key Design Patterns

1. **ActiveRecord / Repository Hybrid:** Core domain models (`Collection`, `RecordModel`, `BaseModel` in `src/core/`) encapsulate data and offer `toJSON()` serialization, while `BaseApp` (`app.save(model)`, `app.delete(model)`) acts as a centralized repository orchestrating persistence, schema synchronization, and event dispatching.
2. **Event-Driven Hook Pipeline (`Hook` / `TaggedHook`):** Operations trigger pre- and post-events (`onRecordValidate`, `onRecordCreate`, `onRecordAfterCreateSuccess`). `TaggedHook` allows binding listeners scoped to specific collection IDs (e.g. `onRecordCreate.bind('posts', handler)`).
3. **Subprocess Sandbox Isolation (JSVM):** Untrusted code or condition nodes can be executed inside isolated Deno subprocesses (`src/tools/jsvm/deno_sandbox.ts`) with restricted flags (`--deny-net`, `--deny-read`, `--deny-write`). Operations fall back to Node `vm.Script` legacy context execution when Deno is unavailable.
4. **Dual SQLite Database Pattern:** Database engine maintains two distinct SQLite files: `data.db` (primary user collections, records, and system schemas) and `auxiliary.db` (auxiliary/cache metadata).

*Inconsistencies Noted:*
- `BaseApp.save()` handles `Collection` and `PBRecord` with custom dynamic SQL generator blocks instead of delegating to dedicated model repositories.
- SQL identifier safety is enforced via manual checks (`validateIdentifier()`) rather than typed AST structures in schema modification paths.

### Traced Data Flows

#### 1. Admin Authentication (`POST /api/admins/auth-with-password`)
1. Client sends `POST /api/admins/auth-with-password` with `{ identity, password }`.
2. Middleware `adminAuthRateLimiter` (`src/apis/admin_auth.ts`) checks IP and identity against max 10 requests per 15-minute window.
3. Handler checks `isLockedOut('admin:<identity>')` from `src/utils/lockout.ts`.
4. Query prepares `SELECT * FROM _superusers WHERE email = ?` on `data.db`.
5. `verifyPassword(password, row.passwordHash)` compares input against bcrypt hash (`src/tools/security/crypto.ts`).
6. On failure, `recordFailedAttempt()` increments counter and returns HTTP 400.
7. On success, `clearAttempts()` resets counter.
8. `app.generateJWT({ id: row.id, type: 'admin' }, app.getJwtSecret(), '720h')` signs JWT.
9. Returns `{ token, admin: { id, email } }`.

#### 2. Record Creation (`POST /api/collections/:collectionIdOrName/records`)
1. Request hits `POST /api/collections/:collectionIdOrName/records` in `src/apis/record_crud.ts`.
2. `loadAuthToken` middleware parses Bearer token and populates `req.admin` or `req.authRecord`.
3. `app.findCollectionByNameOrId()` retrieves `Collection` instance (from in-memory cache or `_collections` table).
4. `evaluateRule(collection.createRule, requestInfo, null)` parses rule string with `parseFilter()` and evaluates AST. Throws HTTP 403 if unauthorized.
5. Constructs `PBRecord(collection.id, collection.name, req.body)`.
6. Validates fields using `field.validate()` for each defined field in collection.
7. Calls `app.save(record)` (`src/core/base.ts`):
   - Triggers `onRecordValidate`, `onRecordCreate`, `onRecordCreateExecute`.
   - Filters keys against `getRecordFieldWhitelist(collection.id)`.
   - Executes `INSERT INTO _r_<collectionId> (id, created, updated, collectionId, collectionName, ...) VALUES (...)`.
   - Triggers `onRecordAfterCreateSuccess`.
8. `EventBroker.publishRecord('create', collection.name, record)` broadcasts event to active SSE and WebSocket listeners.
9. Returns HTTP 200 with record JSON representation.

#### 3. Database Migration Execution (`Solarch.migrate()`)
1. `app.migrate()` (`src/solarch.ts`) instantiates `MigrationRunner(app)` (`src/core/migration.ts`).
2. Reads JavaScript files from `pb_migrations/` directory.
3. Queries `_migrations` table in `data.db` to discover already applied migration IDs.
4. Filters pending migrations by comparing filenames against applied IDs.
5. Opens SQLite transaction `db.transaction(...)`.
6. Executes `up(app)` callback for each pending migration script.
7. Inserts migration record into `_migrations` table (`INSERT INTO _migrations (id, applied) VALUES (?, ?)`).
8. Commits transaction and logs completion.

## 4. Data Layer

- **Database Engine:** Embedded SQLite via `better-sqlite3` v11.0.0.
- **Dual Database Files:**
  - `data.db`: Stores primary system schemas and all record data tables.
  - `auxiliary.db`: Stores auxiliary operational data and transient state.
- **System Tables:**
  - `_collections`: Collection definitions and JSON metadata.
  - `_settings`: Application key-value settings (encrypted via AES-256-GCM when key is present).
  - `_migrations`: Applied migration IDs and timestamps.
  - `_superusers`: Admin account credentials (`email`, `passwordHash`).
  - `_logs`: System logging entries (`level`, `message`, `data`, `created`).
  - `_mfas`: Multi-factor authentication secrets and backup codes.
  - `_otps`: One-time password records.
  - `_authOrigins`: Auth origin device fingerprints.
  - `_externalAuths`: Linked OAuth2 provider IDs.
  - `_tokenRevocations`: Revoked JWT hashes.
  - `_oauth2States`: Active OAuth2 authentication state tokens.
  - `_passwordResetTokens`: Password reset hashes and metadata.
  - `_r_<collectionId>`: Dynamic physical SQLite table for each user collection.
- **SQLite Custom Extensions:**
  - `vector_cosine_similarity(aJson, bJson)` registered on SQLite connection as a deterministic SQL function.
- **Query Builder & AST Engine:**
  - Custom AST filter parser in [src/tools/search/filter.ts](file:///Users/jay/Downloads/solarch/src/tools/search/filter.ts) translating Solarch filter expressions into parameterized SQL `WHERE` clauses and in-memory evaluations.
  - Custom `SqliteQueryBuilder` in [src/tools/search/query-builder.ts](file:///Users/jay/Downloads/solarch/src/tools/search/query-builder.ts).
  - No heavy external ORM (such as Prisma or TypeORM) is used.

### Implemented Authorization Model

1. **Superuser / Admin Authorization:** Verified using JWT payload containing `{ id, type: 'admin' }`. Endpoints requiring admin access use `requireSuperuserAuth(app)` middleware.
2. **Record User Authorization:** Verified using JWT payload containing `{ id, type: 'auth', collectionId }`.
3. **API Rule Expressions:** Each collection defines 5 security rule strings: `listRule`, `viewRule`, `createRule`, `updateRule`, `deleteRule`.
   - `null`: Action is allowed for everyone (public access).
   - `""` (empty string): Action is disallowed for non-admin users.
   - Expression string (e.g. `owner = @request.auth.id`): Parsed into AST and evaluated against request context (`@request.auth`, `@request.query`, etc.) and record fields.

## 7. Configuration & Environment

### Required Environment Variables

- `JWT_SECRET` or `SOLARCH_JWT_SECRET`: Secret key used for signing JWT tokens. **Fatal at startup** if missing or under 32 characters long (`BaseApp.bootstrap()` throws an explicit Error).
- `SETTINGS_ENCRYPTION_KEY` or `SOLARCH_ENCRYPTION_KEY`: Optional 32-character key used for AES-256-GCM encryption of sensitive database settings (SMTP credentials, S3 secrets, AI API keys).

### Optional Environment Variables

- `JSVM_SANDBOX_MODE`: Set to `isolated` to force Deno subprocess execution for condition nodes (defaults to `legacy`).
- `JSVM_MAX_MEMORY_MB`: Memory cap in MB for Deno sandbox subprocess (default: `64`).
- `JSVM_MAX_CONCURRENT`: Maximum concurrent Deno sandbox subprocesses (default: `8`).
- `PORT`: HTTP server port number (default: `8090`).

## 8. Known Gaps

1. **Unimplemented PostgreSQL Support:** The `solarch init` CLI command prompts the user to select `sqlite` or `postgres` and generates a `docker-compose.yml` for PostgreSQL. However, the runtime `DB` class ([src/core/db.ts](file:///Users/jay/Downloads/solarch/src/core/db.ts)) hardcodes `SqliteDriver` and `better-sqlite3`. PostgreSQL is completely unimplemented in the server runtime.
2. **Disabled Method Stub (`findRecordsByRawQuery`):** In [src/core/record_query.ts](file:///Users/jay/Downloads/solarch/src/core/record_query.ts#L232-L239), `findRecordsByRawQuery` explicitly throws `Error('findRecordsByRawQuery is disabled — use findAllRecords or findRecordsByFilter instead')`.
3. **Deno Isolated Sandbox Fallback:** When `JSVM_SANDBOX_MODE=isolated` is set but Deno is not installed on the system host, `JSVM` logs a warning and silently falls back to running condition scripts in Node `vm.Script` legacy context mode ([src/tools/jsvm/jsvm.ts](file:///Users/jay/Downloads/solarch/src/tools/jsvm/jsvm.ts#L46-L50)).
4. **Silent Exception Catch in Automated Backup Cron:** In [src/apis/serve.ts](file:///Users/jay/Downloads/solarch/src/apis/serve.ts#L179), failure to initialize automated backup cron silently catches and ignores error during server startup.
5. **Test Coverage Gaps:** While auth, backup, SQL injection, and JSVM sandbox have high test coverage (155 passing tests across 10 test files), there are currently no automated test files in `__tests__/` covering Record CRUD routes, Collection endpoints, Settings API, File management, Realtime SSE/WS streams, Batch API, or AI endpoints.

- `src/core/events.ts`: Event interface definitions for application lifecycle hooks.
- `src/core/field.ts`: Field definitions and validator classes for collection data types.
- `src/core/migration.ts`: Migration runner (`MigrationRunner`) executing schema updates tracked in `_migrations`.
- `src/core/model.ts`: Abstract base model (`BaseModel`) handling ID generation and JSON serialization.
- `src/core/record.ts`: Dynamic data model (`RecordModel`) representing individual collection records.
- `src/core/record_field_resolver.ts`: Relation expansion and field resolution helper for API outputs.
- `src/core/record_query.ts`: Record query helpers (find by ID, filter, pagination, vector search).
- `src/core/record_upsert.ts`: Record insertion, update, and batch transaction helpers.
- `src/core/schema_sync.ts`: Synchronizes Collection schema metadata with physical SQLite `_r_<collectionId>` tables.
- `src/core/settings.ts`: App settings schema definition and default values.
- `src/core/settings_encrypt.ts`: AES-256-GCM encryption helper for sensitive settings stored in `_settings`.
